# Transaction / activity model

This doc covers the **`Activity`** record in depth: how manual and auto-posted
transactions are unified, how tags attach, how timestamps default to "now" but
are editable, how editing any activity works, and how **Available Funds** is
derived from the activity log.

The `Activity` shape is defined in [data-model.md](data-model.md); this doc is
the *behavioral* contract on top of that shape.

## The unified record

There is exactly **one** kind of transaction record: `Activity`. Whether it was
typed in by the user (manual) or generated by the recurring engine
(auto-posted), it is the same shape, stored in the same object store, queried the
same way, and edited the same way. The only difference is the provenance fields:

```ts
interface Activity {
  id: string;
  type: "income" | "expense" | "deposit";
  amountCents: number;   // positive integer, in minor units (cents); canonical stored shape
  currency: string;
  dateTime: string;      // defaults to "now" at creation, always editable
  tags: string[];
  source: "manual" | "recurring" | "file-import" | "bank-sync";
  sourceRuleId?: string;   // present iff source === "recurring"
  period?: string;         // present iff source === "recurring"
  importBatchId?: string;  // reserved for local CSV/OFX/QFX file import (groups rows from one import batch)
  externalTxnId?: string;  // reserved dedupe key (OFX/QFX FITID, CSV content hash, or bank-feed txn id)
  sourceAccountId?: string;// reserved account label / future linked account id
  memo?: string;
  createdAt: string;
  updatedAt: string;
  deletedAt?: string;      // reserved for future E2EE sync tombstones (unused in MVP; MVP hard-deletes)
  deviceId?: string;       // reserved for future E2EE sync origin attribution (unused in MVP)
}
```

- **`source: "manual"`** → the user typed it in. No `sourceRuleId`, no `period`.
- **`source: "recurring"`** → the engine generated it. Carries `sourceRuleId`
  (which rule) and `period` (which period it was posted for). See
  [recurring-engine.md](recurring-engine.md).
- **`source: "file-import"`** *(post-MVP, first-class privacy-preserving seam)* →
  imported locally from a user-supplied CSV, OFX, or QFX statement. Carries
  `importBatchId` (for batch audit/rollback) and `externalTxnId` (native
  OFX/QFX `FITID` or a deterministic CSV content hash) for idempotent
  deduplication, with zero network egress.
- **`source: "bank-sync"`** *(reserved)* → reserved for opt-in SimpleFIN Bridge
  or a separate future bank-aggregator project (which re-opens Pillar 2; see
  [data-model.md → Privacy-Label Impact and Sync Tradeoffs](data-model.md#privacy-label-impact-and-sync-tradeoffs)).

Because they share one record type, the UI, the query layer, and the Available
Funds calculation all treat them identically. There is no "recurring table" vs.
"transaction table" to keep in sync.

## Tagging

- **`tags: string[]`** is a free-form array on every Activity — manual *or*
  recurring.
- Tagging is **manual** for all records. The user can add/remove tags on an
  auto-generated activity exactly as on a manual one (e.g. tag an auto-posted
  "Rent" activity with `housing` for future analytics).
- Tags are **unconstrained strings** in the MVP (no global tag dictionary, no
  schema). This keeps the MVP small; a shared tag list / autocomplete is a
  future enhancement that does not change the data shape.
- Tags power the **insights/search surface** in the MVP: query activities by
  date range + tag + type, and roll up spend/income **by tag**. See
  [Insights / search](#insights--search).

## Timestamps: default to "now", always editable

- **Default.** At creation, `dateTime` is set to the current time
  (`new Date().toISOString()` unless the caller passes one). So a manual
  "spent $40 on groceries" entered on 2026-11-05 gets `dateTime ≈ now`.
- **Always editable.** `dateTime` is a user-settable field on **every** activity,
  manual and recurring alike. Back-dating an expense to 2026-10-28 is a normal
  edit and is fully supported.
- **Recurring default is the due date at `12:00:00Z`, not "now" (OQ-2).** The
  recurring engine sets a recurring activity's `dateTime` to fixed **`12:00:00Z`**
  (noon UTC) on the clamped **due date** for that period (e.g.
  `2026-11-01T12:00:00Z` for the November period), not the moment the engine ran
  and not `00:00:00Z` (which shifts to the previous day for all UTC− users).
  This keeps the local calendar day accurate across UTC−12 through UTC+11 (with
  UTC+12..+14 documented as an accepted MVP residual in
  [recurring-engine.md](recurring-engine.md#notes-and-resolved-defaults)) and
  remains editable by the user afterwards.
- **`createdAt` / `updatedAt`** are system-managed and are **not** the
  transaction date. They answer "when did this record appear / get last touched",
  distinct from "when did the money move" (`dateTime`).

## Editing any activity

**Every activity is always editable**, manual or auto-generated. The edit
surface is identical:

| Field | Editable | Notes |
| ----- | -------- | ----- |
| `type` | yes | e.g. reclassify an auto-posted "expense" as "deposit" |
| `amountCents` | yes | change the magnitude (integer cents) |
| `dateTime` | yes | back-date or forward-date |
| `tags` | yes | add / remove any |
| `memo` | yes | free text |
| `source`, `sourceRuleId`, `period`, `importBatchId`, `externalTxnId`, `sourceAccountId`, `createdAt`, `updatedAt`, `deletedAt`, `deviceId` | no | system-managed provenance, dedupe keys, audit timestamps, and reserved optional E2EE sync tombstone/origin slots (unused in MVP; MVP hard-deletes); never user-editable |

Consequences that fall out of this design:

- **Editing an auto-posted activity does not touch its rule.** The rule is the
  *origin* of a record, not its *owner*. Edit the activity → the rule is
  unchanged; edit the rule → only *future* periods change
  ([recurring-engine.md](recurring-engine.md)).
- **Editing is a simple upsert.** Because `id` is stable and every field is
  either user-editable or system-managed, an edit is: load → mutate user-editable
  fields → set `updatedAt = now` → `adapter.save("activities", activity)`. No
  special cases for "manual" vs. "recurring".
- **Deletion** is a first-class operation on any activity (manual or recurring),
  `adapter.delete("activities", id)`. In the MVP, deletion **hard-deletes** the
  record from IndexedDB; optional `deletedAt?` and `deviceId?` fields are
  reserved on `Activity` and `RecurringRule` so a future E2EE multi-device sync
  layer can switch to soft-delete tombstones without migrating v1 records (see
  [data-model.md → Post-MVP Extensibility & Growth Seams](data-model.md#post-mvp-extensibility--growth-seams)).
  Deleting a recurring-generated `Activity` removes that record from the activity
  log and does *not* re-post it: because
  `rule.lastPostPeriod` already advanced past that period when it was originally
  posted, `missingPeriods` (which enumerates `(rule.lastPostPeriod, period(now)]`,
  starting from `nextMonth(rule.lastPostPeriod)`) never re-enumerates that period
  and does not resurrect the deleted activity — deletion is the user's intent
  (see [recurring-engine.md → Deleting a recurring-generated activity](recurring-engine.md#deleting-a-recurring-generated-activity);
  if historical range re-evaluation prior to `lastPostPeriod` is ever introduced
  post-MVP, an optional `skippedPeriods?: string[]` array on `RecurringRule`
  preserves user deletions).

## Available Funds — derived from the activity log

**Available Funds is never stored.** It is computed on demand from the whole
activity log:

```
Available Funds = Σ amountCents(activities where type ∈ {income, deposit})
                − Σ amountCents(activities where type === expense)
```

```ts
function computeAvailableFunds(activities: Activity[]): number {
  const totalCents = activities.reduce((sumCents, a) => {
    return a.type === "expense" ? sumCents - a.amountCents : sumCents + a.amountCents;
  }, 0);
  return totalCents; // integer cents (minor units); convert to decimal only at the display boundary
}
```

`computeAvailableFunds` operates on **integer cents** (`amountCents`) — pure
integer addition/subtraction, no `Math.round(a.amount * 100)` and no float
drift. The decimal-unit display is a boundary concern (see
[data-model.md](data-model.md#the-two-core-entities)).

Why derive it:

- **Always consistent.** Any edit to any activity (`amountCents`, type, delete)
  is automatically reflected — there is no separate balance to update, no cache
  to invalidate, and no way for a stored balance to drift from the log.
- **Trivially recomputable.** It is a pure function of the activity list, so it
  is cheap to recompute and trivially unit-testable.
- **The log is the single source of truth.** "Available Funds" is a *view* over
  the log, not a second record that could contradict it.

Note: `deposit` is treated as **money in** in this sum (same sign as `income`).
Whether `deposit` should instead be a distinct kind, or folded into `income`
with a tag, is a **resolved MVP default** (`deposit` is confirmed as a first-class `ActivityType` for the MVP) — see
[portability.md → resolved MVP defaults](portability.md#resolved-mvp-defaults).

## Insights / search

The MVP provides a **fast search-and-summarize surface** over the activity log —
this is what "manual tagging for future insight / analytics" and "search/filter
by period + tag" resolve to. It is a **pure, derived query over `Activity`
records** (no stored aggregates, no analytics engine), so it stays in `core/`,
is trivially unit-testable, and scales to a 5-year history.

Two operations, both returning **plain data** (integer cents, no framework
state):

### 1. `searchActivities(filter)` — filter by intersecting predicates

Query activities by **date range + tag + type**. All supplied predicates are
**intersecting** (logical AND) — omit a predicate to leave it unbounded:

```ts
interface ActivitySearchFilter {
  since?: string;   // ISO-8601 lower bound, inclusive  (e.g. "2026-01-01T00:00:00Z")
  until?: string;   // ISO-8601 upper bound, exclusive  (e.g. "2026-12-01T00:00:00Z")
  tag?: string;     // activity.tags must include this tag
  type?: ActivityType; // income | expense | deposit
}

function searchActivities(activities: Activity[], filter: ActivitySearchFilter): Activity[] {
  return activities.filter((a) =>
    (filter.since === undefined || a.dateTime >= filter.since) &&
    (filter.until === undefined || a.dateTime <  filter.until) &&
    (filter.tag   === undefined || a.tags.includes(filter.tag)) &&
    (filter.type  === undefined || a.type === filter.type)
  );
}
```

- **Date range & recurring period attribution (OQ-2):**
  - Free-form date-range filtering (`searchActivities`) compares `dateTime` (stored UTC) — so "all of 2026" is `since: 2026-01-01T00:00:00Z, until: 2027-01-01T00:00:00Z`. A 5-year window is just a wider range; the filter itself is O(n) over the log, which is fine for local data and is where a storage index on `(dateTime)` / `(tag, dateTime)` can later be slotted in behind the [`StorageAdapter`](storage.md) without changing this contract.
  - **Period rollups use `Activity.period` for recurring items:** Whenever computing monthly or period-based rollups (such as a month summary view or `summarizeByPeriod`), recurring activities (`source === "recurring"`) MUST be bucketed by **`Activity.period`** (e.g. `"2026-11"`) rather than slicing `dateTime` against local-midnight month boundaries, guaranteeing timezone offsets never misattribute a 1st-of-month recurring item to an adjacent month (non-recurring activities bucket by `dateTime`).
- **`tag` + `type`** combine with the range — e.g. *housing expense in Q3 2026*.

### 2. `summarizeByTag(activities)` — roll up by tag

Aggregate a (possibly filtered) activity set into a per-tag rollup of money in
and money out, in **integer cents**:

```ts
interface TagSummary {
  tag: string;
  totalInCents: number;  // Σ amountCents where type ∈ {income, deposit}
  totalOutCents: number; // Σ amountCents where type === expense
}

function summarizeByTag(activities: Activity[]): TagSummary[] {
  const byTag = new Map<string, TagSummary>();
  for (const a of activities) {
    for (const tag of a.tags) {
      let s = byTag.get(tag);
      if (!s) { s = { tag, totalInCents: 0, totalOutCents: 0 }; byTag.set(tag, s); }
      if (a.type === "expense") s.totalOutCents += a.amountCents;
      else s.totalInCents += a.amountCents; // income or deposit
    }
  }
  return [...byTag.values()].sort((x, y) => x.tag.localeCompare(y.tag));
}
```

- All arithmetic is **integer-domain** (`amountCents`), consistent with
  `computeAvailableFunds`.
- An activity with multiple tags contributes its cents to **each** of its tags
  (a rent activity tagged `["housing","rent"]` counts once toward both).
- `deposit` counts as **money in**, matching Available Funds.

Typical composition: `summarizeByTag(searchActivities(all, { since, until, tag, type }))`
gives "where did my money go, by tag, over this period" — the insight the user
asks for, answered entirely from the derived log. These two methods are exposed
on the `BudgetApi` public surface
([portability.md](portability.md#the-public-api-what-the-front-end-calls)).

### 3. Post-MVP Analytics & Category Target Composition

Because `searchActivities` and `summarizeByTag` are pure functions over plain
`Activity` arrays in integer cents, post-MVP analytics and budgeting extensions
([data-model.md → Post-MVP Extensibility & Growth Seams](data-model.md#post-mvp-extensibility--growth-seams))
compose directly with them without changing the MVP contract:

- **Time-series period bucketing (`summarizeByPeriod`):** A post-MVP
  `summarizeByPeriod(activities: Activity[], granularity: "month" | "quarter" | "year")`
  function in `src/core/insights.ts` groups any `searchActivities(all, { since, until, tag, type })`
  slice by period key (`"2026-11"`, `"2026-Q4"`, `"2026"` — using
  `Activity.period` where `source === "recurring"` and UTC `dateTime` for
  non-recurring records, per OQ-2) and delegates each
  bucket's tag breakdown to `summarizeByTag(bucketActivities)`, powering multi-period
  trend comparisons and cash-flow forecasting in integer cents.
- **Category envelopes / spending targets (`BudgetTarget`):** A post-MVP
  `"budgetTargets"` store (`{ id, tag, monthlyTargetCents, rollover }`) joins
  against `summarizeByTag(await budget.searchActivities({ since, until }))` on
  `target.tag === summary.tag`. Envelope remaining balance is simply
  `target.monthlyTargetCents + rolloverCents - summary.totalOutCents` in integer
  cents—requiring zero changes to `Activity` or `summarizeByTag`.
- **Split transactions (`Activity.splits`):** When an optional
  `splits?: Array<{ amountCents: number; tags: string[]; memo?: string }>` array
  is present on an `Activity` (with `sum(splits.amountCents) === activity.amountCents`),
  `computeAvailableFunds` continues summing top-level `activity.amountCents`
  unchanged, while `searchActivities` (for `filter.tag`) and `summarizeByTag`
  iterate each split's `(amountCents, tags)` pair instead of the parent record's
  `tags`—preserving exact cent-level reconciliation across split categories.

## Mapping the user's ask → activity model

| User's ask | Model answer |
| ---------- | ------------ |
| "add expenses or deposits" (manual) | `Activity { type: "expense"\|"deposit", source: "manual" }` |
| "automatically add recurring income and expense" | engine creates `Activity { source: "recurring", sourceRuleId, period }` |
| "all activity is editable" | every user-editable field on every Activity, manual or recurring |
| "defaulted to the current time, with the ability to change it" | `dateTime` defaults to now, always editable |
| "manual tagging for future insight / analytics" | `tags: string[]` on every Activity |
| "search/filter by period + tag" | `searchActivities({ since, until, tag, type })` (Insights / search) |
| "analyze by tag over a period" | `summarizeByTag(searchActivities(...))` (Insights / search) |
| "Available Funds = income minus expenses" | derived from the activity log (above) |
| "change recurring expenses/income whenever I want (without losing history)" | edit the `RecurringRule`; posted Activities are independent and preserved |
