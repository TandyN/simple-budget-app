# Transaction / activity model

This doc covers the **`Activity`** record in depth: how manual and auto-posted
transactions are unified, how tags attach, how timestamps default to "now" but
are editable, how editing any activity works, and how **Available Funds** is
derived from the activity log.

The `Activity` shape is defined in [data-model.md](data-model.md); this doc is
the *behavioral* contract on top of that shape.

## The unified record

There is exactly **one** kind of transaction record: `Activity`. Whether it was
typed in by the user (manual) or generated by the recurring engine
(auto-posted), it is the same shape, stored in the same object store, queried the
same way, and edited the same way. The only difference is the provenance fields:

```ts
interface Activity {
  id: string;
  type: "income" | "expense" | "deposit";
  amount: number;
  currency: string;
  dateTime: string;      // defaults to "now" at creation, always editable
  tags: string[];
  source: "manual" | "recurring";
  sourceRuleId?: string; // present iff source === "recurring"
  period?: string;       // present iff source === "recurring"
  memo?: string;
  createdAt: string;
  updatedAt: string;
}
```

- **`source: "manual"`** → the user typed it in. No `sourceRuleId`, no `period`.
- **`source: "recurring"`** → the engine generated it. Carries `sourceRuleId`
  (which rule) and `period` (which period it was posted for). See
  [recurring-engine.md](recurring-engine.md).

Because they share one record type, the UI, the query layer, and the Available
Funds calculation all treat them identically. There is no "recurring table" vs.
"transaction table" to keep in sync.

## Tagging

- **`tags: string[]`** is a free-form array on every Activity — manual *or*
  recurring.
- Tagging is **manual** for all records. The user can add/remove tags on an
  auto-generated activity exactly as on a manual one (e.g. tag an auto-posted
  "Rent" activity with `housing` for future analytics).
- Tags are **unconstrained strings** in the MVP (no global tag dictionary, no
  schema). This keeps the MVP small; a shared tag list / autocomplete is a
  future enhancement that does not change the data shape.
- Tags are the seed for **future analytics** (group-by-tag rollups). They are
  *captured now* and *used later* — analytics features are out of MVP scope.

## Timestamps: default to "now", always editable

- **Default.** At creation, `dateTime` is set to the current time
  (`new Date().toISOString()` unless the caller passes one). So a manual
  "spent $40 on groceries" entered on 2026-11-05 gets `dateTime ≈ now`.
- **Always editable.** `dateTime` is a user-settable field on **every** activity,
  manual and recurring alike. Back-dating an expense to 2026-10-28 is a normal
  edit and is fully supported.
- **Recurring default is the due date, not "now".** The recurring engine sets a
  recurring activity's `dateTime` to the **due date** for that period (e.g.
  `2026-11-01` for the November period), not the moment the engine ran. This is
  the natural "the transaction happened on the 1st" semantics and is still
  editable by the user afterwards.
- **`createdAt` / `updatedAt`** are system-managed and are **not** the
  transaction date. They answer "when did this record appear / get last touched",
  distinct from "when did the money move" (`dateTime`).

## Editing any activity

**Every activity is always editable**, manual or auto-generated. The edit
surface is identical:

| Field | Editable | Notes |
| ----- | -------- | ----- |
| `type` | yes | e.g. reclassify an auto-posted "expense" as "deposit" |
| `amount` | yes | change the magnitude |
| `dateTime` | yes | back-date or forward-date |
| `tags` | yes | add / remove any |
| `memo` | yes | free text |
| `source`, `sourceRuleId`, `period` | no | provenance is fixed at creation; an edit never re-attributes origin |

Consequences that fall out of this design:

- **Editing an auto-posted activity does not touch its rule.** The rule is the
  *origin* of a record, not its *owner*. Edit the activity → the rule is
  unchanged; edit the rule → only *future* periods change
  ([recurring-engine.md](recurring-engine.md)).
- **Editing is a simple upsert.** Because `id` is stable and every field is
  either user-editable or system-managed, an edit is: load → mutate user-editable
  fields → set `updatedAt = now` → `adapter.save("activities", activity)`. No
  special cases for "manual" vs. "recurring".
- **Deletion** is a first-class operation on any activity (manual or recurring),
  `adapter.delete("activities", id)`. Deleting a recurring activity does *not*
  re-post it (the idempotency guard checks `(sourceRuleId, period)`; if the user
  deleted it, the engine treats that period as handled and does not resurrect it
  — deletion is the user's intent).

## Available Funds — derived from the activity log

**Available Funds is never stored.** It is computed on demand from the whole
activity log:

```
Available Funds = Σ amount(activities where type ∈ {income, deposit})
                − Σ amount(activities where type === expense)
```

```ts
function computeAvailableFunds(activities: Activity[]): number {
  return activities.reduce((sum, a) => {
    return a.type === "expense" ? sum - a.amount : sum + a.amount;
  }, 0);
}
```

Why derive it:

- **Always consistent.** Any edit to any activity (amount, type, delete) is
  automatically reflected — there is no separate balance to update, no cache to
  invalidate, and no way for a stored balance to drift from the log.
- **Trivially recomputable.** It is a pure function of the activity list, so it
  is cheap to recompute and trivially unit-testable.
- **The log is the single source of truth.** "Available Funds" is a *view* over
  the log, not a second record that could contradict it.

Note: `deposit` is treated as **money in** in this sum (same sign as `income`).
Whether `deposit` should instead be a distinct kind, or folded into `income`
with a tag, is an **open decision** — see
[portability.md → open decisions](portability.md#open-decisions).

## Mapping the user's ask → activity model

| User's ask | Model answer |
| ---------- | ------------ |
| "add expenses or deposits" (manual) | `Activity { type: "expense"\|"deposit", source: "manual" }` |
| "automatically add recurring income and expense" | engine creates `Activity { source: "recurring", sourceRuleId, period }` |
| "all activity is editable" | every user-editable field on every Activity, manual or recurring |
| "defaulted to the current time, with the ability to change it" | `dateTime` defaults to now, always editable |
| "manual tagging for future insight / analytics" | `tags: string[]` on every Activity |
| "Available Funds = income minus expenses" | derived from the activity log (above) |
| "change recurring expenses/income whenever I want (without losing history)" | edit the `RecurringRule`; posted Activities are independent and preserved |
